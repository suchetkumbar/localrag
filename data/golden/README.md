# Golden dataset: data card

Question/answer/evidence triples for evaluating RAG over the FastAPI documentation.
The evaluation harness only uses items a human has verified.

## Files

| File | What it is |
|---|---|
| `v1.jsonl` | **The dataset.** Human-verified items only, built by `python -m rag.golden build`. |
| `drafts.jsonl` | Every LLM-drafted candidate with its review decision (accepted / edited / rejected / pending). Kept as the audit trail. |
| `../manifests/fastapi.json` | The pinned corpus: FastAPI release `0.162.5`, commit, URL and sha256 of every source file. |

All data files are git-ignored and kept locally; only this data card is in the repository.
The manifest can be regenerated with `python -m rag.corpus build-manifest --ref 0.162.5`.

## Corpus

The English FastAPI docs (`docs/en/docs/**/*.md`) at the commit pinned in the manifest,
**excluding** `release-notes.md` (a large changelog that would dominate retrieval),
`reference/` (auto-generated API stubs with no prose) and `_*.md` (translation-tool
fixtures). Code examples referenced with `{* ../../docs_src/... *}` are inlined as fenced
code blocks, and `{ #anchor }` suffixes are removed from headings. Rebuild with:

```bash
python -m rag.corpus fetch      # download + sha256-verify every file in the manifest
python -m rag.corpus prepare    # write data/corpus/fastapi + CORPUS_FINGERPRINT
```

Every item records the `corpus_fingerprint` it was built against; `validate` and `build`
refuse to run against a corpus that differs in any byte.

## Item schema

```json
{
  "id": "nu-1a2b3c4d",
  "question": "Which status code does FastAPI return for invalid request data?",
  "reference_answer": "422 (Unprocessable Entity).",
  "question_type": "numeric",
  "evidence": [{"doc_id": "tutorial/body.md", "start": 1200, "end": 1268, "quote": "..."}],
  "human_verified": true,
  "review": {"status": "accepted", "reviewer": "human", "reviewed_at": "...", "note": ""},
  "provenance": {"drafted_by": "ollama/llama3", "draft_prompt": "<hash>", "source_chunks": ["..."]},
  "corpus_fingerprint": "<sha256>"
}
```

* **Evidence is a character span** in a prepared document (`doc_id`, `start`, `end`) plus
  the exact quoted text. Spans, unlike chunk IDs, do not depend on the chunking strategy.
  A retrieved chunk counts as relevant if it overlaps an evidence span, which is how one
  set of labels can score both the fixed-size and the heading chunker.
* `question_type`:
  * `factual`: answered by one passage.
  * `numeric`: the answer is a specific number (status code, port, version, count, default).
  * `multi_hop`: needs two evidence spans; the answer combines both.
  * `unanswerable`: the corpus does not answer it. The correct behaviour is to refuse, and
    `reference_answer` is the pipeline's fixed refusal sentence.
* `human_verified` is true exactly when `review.status` is `accepted` or `edited`; the
  schema rejects any other combination. `load_golden()` refuses unverified items.

## How it was built

1. **Drafting** (`python -m rag.golden draft`, settings in `configs/drafting.yaml`). Corpus
   sections are sampled with a fixed seed, at most 4 items per document. A local LLM gets
   each section split into numbered units (sentences, list items, code blocks) and returns
   a question, an answer and the *unit numbers* that support it. Evidence offsets come
   from our own unit splitter, never from text the model wrote, so every span exists
   verbatim in the corpus. Multi-hop drafts see two sections of the same page; unanswerable
   drafts are asked for a plausible question the section does not answer. Drafts that leak
   the setup ("according to the passage"), lack a number (numeric), cite only one passage
   (multi-hop) or nearly duplicate an earlier question are discarded automatically.
   Drafting is oversampled (260 candidates) because review rejects some.
2. **Review** (`python -m rag.golden review`). A human sees each candidate with its evidence
   highlighted in context and accepts, edits (question, answer, type, evidence spans) or
   rejects it. For unanswerable candidates the tool shows the three closest corpus passages
   by BM25, so the reviewer can check the question really is unanswerable.
3. **Build** (`python -m rag.golden build`). Takes the first verified items of each type in
   draft order up to fixed quotas: 110 factual, 30 numeric, 40 multi-hop, 20 unanswerable
   (200 items, 10% unanswerable). Every evidence quote is re-checked against the corpus.

## Known limitations

* **Lexical bias.** Questions drafted from a passage tend to reuse its wording, which favours
  lexical retrieval (BM25) over dense retrieval compared to real user questions. Reviewers
  should rephrase obviously copied questions when editing. Treat BM25-vs-dense differences
  on this set with that bias in mind.
* **One reviewer.** Each item is checked by a single person, so there is no inter-annotator
  agreement figure for the labels themselves.
* **Multi-hop items stay within one page.** Pairs are drawn from sections of the same
  document, so cross-document reasoning is under-represented.
* **"Unanswerable" is checked, not proven.** The reviewer checks the closest BM25 passages,
  not the whole corpus; an answer phrased very differently could exist.
* **Small-model drafts.** Drafts come from an 8B local model. Review removes bad items, but
  the question styles reflect that model's habits.
* **English only, one corpus version.** Results do not transfer automatically to other
  FastAPI versions; a new version needs a new manifest and a re-validated dataset.
